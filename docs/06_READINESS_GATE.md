# Validation Contract — V1 to V7

- 대상 작업: `[계획 링크]`
- 평가자: `[사용자/agent/reviewer]`
- 평가일: `YYYY-MM-DD`
- 구현 전 판정: `NOT_REVIEWED | PASS | CONDITIONAL | BLOCKED`
- 구현 후 판정: `NOT_REVIEWED | PASS | CONDITIONAL | BLOCKED`

이 문서는 계획을 실행 가능한 계약으로 바꾸고, 구현 후 동일한 기준으로 결과를 다시 검증하기 위한 템플릿입니다. 큰 기능과 위험한 변경에 적용합니다. 작은 Quick Fix는 영향 범위에 맞는 검증만 기록할 수 있습니다.

## 판정 규칙

- `PASS`: 모든 필수 체크포인트가 실행 가능하고 차단 조건이 없다.
- `CONDITIONAL`: 구현 가능하지만 미해결 조건, 담당자, 기한, 실패 영향이 명시돼 있다.
- `BLOCKED`: 범위, 계약, 보안, 검증 또는 롤백 공백 때문에 안전하게 구현할 수 없다.

## Project Baseline Readiness

새 서비스 또는 큰 기능은 V1~V7 판정 전에 아래 15개 항목을 `0=없음`, `1=부분적`, `2=제3자가 같은 결과를 만들 수 있을 정도로 명확`으로 점검합니다. 권장 시작선은 **26/30 이상이며 0점 항목 없음**입니다. 이 수치는 초기 기본값이므로 실제 프로젝트의 재작업·과잉 문서화 사례를 기록해 팀에 맞게 조정합니다.

## Validation Checkpoints

| ID | Checkpoint | 구현 전 질문 | 구현 후 필요한 증거 | 판정 |
|---|---|---|---|---|
| V1 | Intent & Scope | 목표, 포함·제외 범위, 요구사항 ID가 일치하는가? | 변경 결과가 승인 범위 안에 있음을 보여주는 diff/리뷰 | `PASS/CONDITIONAL/BLOCKED` |
| V2 | Architecture Fit | 기존 경계와 의존 방향을 지키는가? ADR이 필요한가? | 영향 구성요소와 의존성 검토 결과 | `PASS/CONDITIONAL/BLOCKED` |
| V3 | Contracts | 화면·API·데이터·상태·권한 계약이 완전한가? | 계약 테스트, schema diff, 주요 UI 상태 확인 | `PASS/CONDITIONAL/BLOCKED` |
| V4 | Security & Data | 인증, 권한, 비밀, 개인정보, migration 위험을 다뤘는가? | 보안 검사, 권한 테스트, migration/rollback 결과 | `PASS/CONDITIONAL/BLOCKED` |
| V5 | Verification | 각 AC를 확인할 명령·환경·기대값이 있는가? | 독립 재실행한 테스트·lint·typecheck·build 결과 | `PASS/CONDITIONAL/BLOCKED` |
| V6 | Operations & Rollback | 장애 감지, 관측, 배포, 되돌리기 방법이 있는가? | 배포 전 점검, 로그/지표, 롤백 확인 결과 | `PASS/CONDITIONAL/BLOCKED` |
| V7 | Traceability & Closeout | 요구사항→계획→코드→테스트 연결과 갱신 대상이 명확한가? | 완료 계획, evidence, context·docs 업데이트 기록 | `PASS/CONDITIONAL/BLOCKED` |
