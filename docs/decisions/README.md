# Architecture Decision Records

이 디렉터리는 프로젝트의 장기적인 구조와 운영에 영향을 주는 결정의 **맥락, 선택, 결과**를 기록합니다. 현재 상태의 요약은 `../02_ARCHITECTURE.md`, 결정의 역사와 근거는 ADR이 담당합니다.

## 프로젝트 시작 전 사용자가 답해야 할 질문

- 어떤 종류의 결정을 ADR로 남길 것인가? `[답변: 예—프레임워크, 데이터 저장소, 인증 방식, 외부 서비스, 배포 구조]`
- 누가 ADR을 제안하고 누가 승인하는가? `[답변]`
- 어느 시점부터 결정이 적용되는가? `[답변]`
- 결정을 바꾸거나 폐기할 때 어떤 절차를 따르는가? `[답변]`
- 과거 결정을 삭제하지 않고 어떻게 상태를 표시할 것인가? `[기본값: SUPERSEDED 또는 DEPRECATED]`

## ADR이 필요한 경우

- 여러 합리적 대안 중 하나를 선택한다.
- 변경 비용이 크거나 되돌리기 어렵다.
- 보안, 개인정보, 성능, 비용, 확장성에 중요한 영향을 준다.
- 팀원이 나중에 "왜 이렇게 했는가?"라고 물을 가능성이 높다.
- 기존 결정과 아키텍처 원칙을 바꾼다.

사소하고 쉽게 되돌릴 수 있는 구현 세부사항은 ADR이 필요하지 않습니다.

## 사용 방법

1. `ADR-000-template.md`를 복사합니다.
2. 다음 번호와 짧은 kebab-case 제목으로 이름을 만듭니다. 예: `ADR-001-use-postgresql.md`.
3. 상태를 `PROPOSED`로 두고 대안과 trade-off를 기록합니다.
4. 승인되면 상태를 `ACCEPTED`로 바꾸고 `../02_ARCHITECTURE.md`에서 링크합니다.
5. 결정이 바뀌면 원본을 삭제하지 말고 새 ADR에서 대체한 뒤 원본을 `SUPERSEDED`로 표시합니다.

## 상태 값

- `PROPOSED` — 검토 중
- `ACCEPTED` — 승인되어 적용 중
- `REJECTED` — 검토 후 채택하지 않음
- `DEPRECATED` — 더 이상 권장하지 않음
- `SUPERSEDED` — 새로운 ADR로 대체됨
